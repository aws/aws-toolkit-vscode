## Verdict

**Approve with minor comments.** The VS Code implementation is behaviorally equivalent to the
JetBrains managed installer/launcher on every point in the parity checklist below. The only
semantic deviations are deliberate and are improvements (see "Intentional deviations"). I found one
real (edge-case) bug in the restart path, one robustness gap for malformed manifests, and a handful of
test/style nits. Nothing blocking.

## Intentional deviations (fine, but worth a code comment / PR note)

1. **Cached-manifest + `NoCompatibleVersion` falls back to an installed server.** `baseLspInstaller.ts:113`
   treats `NoCompatibleVersion` from a _cached_ manifest as an offline condition and uses
   `resolveFromInstalledServers()`, re-labelling the error as `ManifestFetchFailed`. JetBrains
   propagates `NO_COMPATIBLE_VERSION` regardless of manifest source. VS Code's behaviour is more
   lenient and arguably better (a stale cache shouldn't brick the user offline), but it is a
   divergence from the "this should be equivalent to JetBrains" claim in the description — call it
   out explicitly.
2. **ZIP entries with no recorded Unix mode keep umask defaults.** `lspResolver.ts:712`
   (`zipEntryPosixMode` returns `undefined` for mode 0 → no `chmod`). JetBrains'
   `ZipDecompressor.createFile` unconditionally calls `setPosixFilePermissions(convertPermissions(unixMode))`,
   which for a Windows-built archive yields an _empty_ permission set. VS Code is strictly better here.
3. **Symlink ZIP entries** are written as regular files containing the link target in both
   implementations (JetBrains has a TODO). Parity, not a regression; noting for completeness.

## Findings

### F1 — Restart while a start is in flight can tear down the _new_ session (bug, edge case)

`extension.ts:176-208`. `startClient` does:

```ts
try {
    const client = await launcher.start()
    await setupPostStart(client, serverProvider)
} catch (error) {
    await disposeClientSession() // uses module-level `launcher` / `clientDisposables`
    throw error
}
```

Sequence: activation starts `launcher#1` (long download) → user runs _Restart Server_ →
`restartClient` → `disposeClientSession()` (sets `launcher = undefined`, disposes `#1`) →
`startClient` creates `launcher#2` and awaits it → `#1.doStart` finishes, sees `disposed`, throws
`LspLauncherDisposed` → **`startClient#1`'s catch calls `disposeClientSession()` and disposes
`launcher#2`** (and clears `clientDisposables` if `#2` already populated them). `startClient#2`
then fails with `LspLauncherDisposed` and the user sees "Failed to restart …".

Fix: capture the launcher in a local and only dispose if it is still current, e.g.

```ts
const thisLauncher = new LspLauncher({...}); launcher = thisLauncher
try { ... } catch (error) {
    if (launcher === thisLauncher) { await disposeClientSession() }
    throw error
}
```

(or simply skip cleanup when `error.code === 'LspLauncherDisposed'`).

### F2 — Malformed manifest entries surface as `TypeError`, not a coded `ToolkitError` (robustness)

`CfnManifestAdapter.adapt` (`lspInstaller.ts:75`) casts `envVersions as CfnLspVersion[]` without
validating elements. A version object lacking `targets` reaches
`findCompatibleTarget` (`targetResolver.ts:56`, `version.targets.find`) and throws a raw
`TypeError` out of `latestCompatibleLspVersion()`, _before_ the resolver's try/fallback. In
`BaseLspInstaller.resolve` the `manifest.location === 'cache'` branch only matches
`NoCompatibleVersion`, so the user gets an uncoded error and no fallback to an installed server.
JetBrains fails at Jackson deserialization (→ cached manifest → installed server).

Cheap fix: `version.targets?.find(...)` in `findCompatibleTarget` and/or filter non-object /
`!Array.isArray(v.targets)` entries in the adapter (or `parseAndAdapt`) so the failure becomes a
manifest parse error and follows the existing offline path.

### F3 — `resolvedInstallation` is not cleared when a re-install of the same version fails (minor parity gap)

JetBrains `removeFailedInstall` CASes `resolvedVersionDir` to `null` if it still points at the
directory just deleted (tests: "a failed reinstall of the resolved version clears the now-deleted
resolved directory"). In VS Code, `LanguageServerResolver.removeFailedInstall` has no access to
`BaseLspInstaller.resolvedInstallation`, and the base only overwrites it on success. Today this is
unreachable in practice because `RemoteLspServerProvider` caches `serverPath` and only re-resolves
after `invalidateResolvedInstallation()` (which clears the field), so the worst case is
`cleanupAfterResolve` retaining a name that no longer exists. Consider clearing
`this.resolvedInstallation` at the top of `BaseLspInstaller.resolve()` to make the invariant explicit.

### F4 — Tautological tests (test quality)

`targetResolverAndTelemetry.test.ts:296-335` "telemetry initialization options" defines a local
`computeClientIdForInit` that _re-implements_ the expression from `extension.ts` and then asserts on
it. These tests can never fail when production code changes. Either export a small
`clientIdForInit(telemetryEnabled, clientId)` helper from `extension.ts`/`utils.ts` and test that,
or drop the block.

### F5 — Shared storage directory with JetBrains: document the race (design note)

Both toolkits now install into `<cache>/aws/language-servers/cloudformation-languageserver/<version>`
and both run "delete everything except current + one fallback" cleanup. Concurrent first starts of
both IDEs can (a) write the same version dir simultaneously, (b) have one side's
`removeFailedInstall`/`cleanupAfterResolve` delete a dir the other side is validating. Identical
bytes make (a) mostly benign, and (b) is recovered by the launcher's invalidate-and-retry, but this
is a new failure mode the previous `aws/toolkits/language-servers` path didn't have. Worth a
sentence in the PR description / a comment near `cfnStorageDir()`.

### F6 — Nits / style

-   `lspResolver.ts:188` `zipEntryEscapesRoot` is exported but only used by tests; it duplicates
    `resolveWithinRoot` with a synthetic root. Either mark `@internal`/`/** exported for tests */`
    or test `resolveWithinRoot` behaviour through `buildInstallPlan` (already covered by the zip-slip
    test).
-   `lspServerProvider.ts` `LspServerResolverI` is structurally identical to
    `shared/lsp/lspLauncher.ts` `LspServerResolver`; re-export/alias one to avoid drift.
-   `lspInstaller.ts:120,130-138,155` use sync `fs` (`statSync`, `existsSync`, `readdirSync`) on the
    extension host while the rest of the module is async; `resourcePaths()` is called on every
    resolve. Small, but inconsistent with the "Node fs, not the wrapper" comment in the resolver which
    at least uses `fs/promises`.
-   `remoteLspServerProvider.ts:12` constructs `CfnLspInstaller` eagerly in a field initializer;
    `cfnStorageDir()` → `fs.getCacheDir()` throws on Windows when `LOCALAPPDATA` is unset, which
    now fails in `new LspServerProvider([...])` (inside `startClient`) with `LocalAppDataNotFound`
    rather than as a provider error. Pre-existing-ish, but lazy construction in `serverExecutable()`
    would let `LspServerProvider` report it via `AllProvidersFailed`.
-   `manifestResolver.ts` `fetchFn?: typeof fetch` vs `lspResolver.ts` `fetchFn?: (url, timeout) => Promise<ArtifactFetchResponse>` — two different injection shapes for the same concern.
-   `baseLspInstaller.ts` builds `new Range(supportedVersionRange, { includePrerelease: true })`
    three times; compute once in the constructor.
-   `downloadContent`: on a non-200 response the body is never consumed before retrying; with
    cross-fetch/node-fetch this can hold the socket until GC. `await response.arrayBuffer().catch(() => {})`
    or `response.body?.destroy()` before throwing is cheap.
-   Commit history on the branch (`Fix tests`, `more fixes`, `Fix lsp`, `revert change`, `test fixes`) — fine
    since the repo squash-merges, but the squash message should be the PR body.

## Things I checked and found correct (no action)

-   `fs.rename` wrapper passes `overwrite: true`, so the manifest cache is actually refreshed after
    the first save.
-   `createHash()` returns `algo:hex`; the resolver strips the prefix before comparing, so
    `sha256/384/512` manifest hashes verify correctly (tests cover all three).
-   `LspLauncher.start()` de-duplicates concurrent callers via `startPromise`, and `dispose()` during
    an in-flight start stops the candidate and throws `LspLauncherDisposed` (tests cover both races).
-   `LspServerProvider.invalidateResolvedInstallation()` clears its own cache and fans out to
    `RemoteLspServerProvider` → `CfnLspInstaller`, so the launcher's second attempt really
    re-downloads.
-   `cleanLspDownloads` unlinks directory symlinks non-recursively, so a symlinked fallback dir can't
    cause deletion of its target.
-   `registerStatusBarCommand()` is guarded by `statusBarRegistered`, fixing the duplicate-command
    registration on _Restart Server_.
-   E2E `waitForLspReady` replaces the fixed 10 s sleep with a bounded (30 s) completion probe; good.
-   `.changes/next-release/Feature-*.json` present and describes user-visible behaviour.
